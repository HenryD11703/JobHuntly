# Architecture

JobHuntly is an interview notebook: a job-search tracker whose unit is the **interview**, not the application. This page explains how it is built and, more usefully, **why**, including what was considered and rejected. The long form of the reasoning lives in `docs/02-plan.md`.

## Shape of the system

```
Browser ──► Next.js 16 (Vercel) ──rewrite /api/*──► ASP.NET Core 8 (Fly.io, Docker) ──► PostgreSQL (Neon)
                                                              └──► Groq (AI drafts, server-side only)
                                                              └──► open.er-api.com (suggested exchange rates)
```

- **Frontend:** Next.js App Router, React 19, TypeScript strict, one global stylesheet (the "Wayfinding" design). Client components talk to the API through a small typed client (`src/lib/api.ts`). No state library: server data plus local state is enough.
- **Backend:** ASP.NET Core 8 with Clean Architecture: `Domain` (entities) ← `Application` (services, calculators, contracts) ← `Infrastructure` (EF Core, Groq, rates, repositories) ← `Api` (controllers, middleware).
- **Database:** PostgreSQL through EF Core and Npgsql. Migrations run at startup (one instance; documented trade-off).

## Decisions and the alternatives we rejected

| Decision | Why | Rejected |
|---|---|---|
| Keep the C# backend, move SQL Server to PostgreSQL | SQL Server has no usable free host; Neon is permanent and free. The Infrastructure layer is isolated, so the swap was small | Rewriting the backend in Next route handlers (cheaper to deploy but removes the part that differentiates the project); Azure free tiers (conflicting terms); Render free (about 1 minute cold start, free Postgres expires in 30 days) |
| Auth: JWT in an `HttpOnly` cookie through a same-origin proxy | The browser only talks to the frontend origin, so the cookie is first-party. No token in `localStorage`, no third-party-cookie problems in Safari. Verified end to end | Token in `localStorage` (readable by any XSS); `SameSite=None` cross-site cookies (blocked by some browsers) |
| CSRF: a required `X-Requested-With` header on every write, plus `SameSite=Lax` | Browsers will not add a custom header to a cross-site form post | Anti-forgery tokens (more state for no gain here) |
| The **interview** is the unit | Prepare, debrief and learn across rounds is the product. A Kanban board alone is a commodity | A plain tracker |
| Deterministic core, AI as an assistant | Nudges, funnel numbers, offer comparison and quotas are plain code with boundary tests. AI only drafts; the user confirms before anything is saved; the app works with AI off | Letting a model decide reminders or numbers |
| Timeline events as the source of truth for insights | The funnel counts stages **reached**, so a rejected application still counts for every stage it passed | Reading only the current status |
| Exchange rates are *suggested*, never applied | The comparison always uses the rates the user saved, so numbers never change under them | Fetching on every page load |
| Errors as RFC 7807 problem details with stable codes | The frontend can switch on `ai_quota_exceeded` or `ai_unavailable`; no internals leak | Catching `Exception` and returning 400 |
| Enums travel as strings | `"Interviewing"` is readable in the API and in the database | Numeric enums |
| Ids are generated by the application (`ValueGeneratedNever`) | A new child added to a tracked parent is inserted, not updated | Database-generated keys |
| Same-origin `/api/*` rewrite resolved at **build** time | Next evaluates `rewrites()` at build time; the backend URL is configuration, never in browser code | Calling the backend from the browser |

## The AI boundary

Three features (extract a pasted job post, suggest likely questions, structure debrief notes) go through `IAiClient`, implemented by a Groq client and faked in every test.

1. **Gate:** no key means the buttons disappear; a daily allowance (30, or 8 in the demo) is consumed with one atomic SQL statement, so parallel requests cannot slip past it, and is given back if the call fails.
2. **Prompt:** pasted text is wrapped in tags declared untrusted, and any attempt to close or reopen those tags from inside the text is neutralised.
3. **Validation:** the answer must parse into an explicit schema. Wrong types, non-JSON or runaway-long strings are rejected after one retry; slightly long lists or strings are trimmed, because models often exceed limits a little. Story ids the model returns must be ones we sent.
4. **Draft:** the result is shown for review. The only thing saved without confirmation is the generated question list, so it is not regenerated on every view.

Prompt injection cannot be eliminated, which is why the defences are layered and why nothing a model produces is ever executed or saved on its own.

## Testing

- **Backend (xUnit):** unit tests for every calculator with boundary cases (the 7-day follow-up at 6 d 23 h and at exactly 7 d), integration tests against a real PostgreSQL (isolation checks for every user-data endpoint, rate limits, cookies, quotas, the demo sandbox), and opt-in tests that call the real services.
- **Frontend:** Vitest for pure logic; Playwright end to end on desktop and a 375 px phone viewport, with axe accessibility checks on every screen. The two third-party services are replaced by a local mock, so no test touches the internet.
- **Real services:** run on demand with `RUN_REAL_API_TESTS=1`. Used to verify the Groq model still exists and still answers in the shape we validate, and that the rates API includes GTQ.

## Known limits

- Migrations run at startup: fine for one instance, not for several.
- The follow-up reminder window (7 days), the AI allowances and the demo lifetime (24 h) are constants chosen for this product, not user settings.
- No tax calculation: offers are compared gross, as entered.
- The Neon free database suspends when idle, so the first request after a quiet period is slower.
